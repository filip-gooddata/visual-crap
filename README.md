# Visual CRAP

An informational, offline interactive call map overlaid with CRAP scores. It analyzes TypeScript and JavaScript source with Fallow and Graphify. It is not a CI gate.

## Run

Requirements: Python 3.9+, Node.js and npm. Install the graph extractor in a virtual environment, then run the tool against a project:

```sh
python3 -m venv .venv
.venv/bin/pip install graphifyy==0.9.97
.venv/bin/python visual_crap.py --root /path/to/project --source src --coverage /path/to/project/coverage/coverage-final.json --output /tmp/visual-crap.html
```

Open the generated HTML in a modern browser supporting `DecompressionStream`. It embeds report data and runs without a server. The output contains source paths and function names: handle it as project data. `npx` downloads Fallow 3.35.0 if needed. Omit `--coverage` to use Fallow's estimates; supply an Istanbul-format report generated by the target project's tests for measured coverage. With Vitest 4, explicitly include the production source glob in coverage so unimported files are instrumented. Run tests successfully before generating the report. `--health` accepts an existing Fallow JSON report instead of invoking Fallow. Reports must correspond to the same source snapshot; staleness cannot be detected. The displayed Git HEAD does not capture uncommitted changes.

Test files, declarations and common test-support directories are excluded from the map and graph extraction. A target project's own test runner still executes tests to measure production coverage. Fallow may exclude additional files; consult its diagnostics. This is an experimental tool: check matches and coverage provenance before relying on results.

## Reading the map

Fallow computes CRAP = complexity² × (1 − coverage/100)³ + complexity. Measured Istanbul statement coverage and static estimates are distinct: grey represents estimated or unknown coverage. The file table ranks each file by its highest measured function score, not an average; files with no measured functions are omitted. Select a row or use search to focus a function. Hover to inspect the score, complexity, coverage and retained relationships.

Measured scores use a continuous green-to-red logarithmic scale, saturated at 100. Within an 18-pixel radius, each measured score contributes through a smooth radial kernel `(1 − (distance / 18)²)²`. Its normalized log score `r = min(1, log(1 + CRAP) / log(101))` has weight `kernel × (1 + 100r²)`; the weighted mean determines color. High scores dominate while other measured scores contribute. Opacity increases with accumulated density and a blur softens edges. This is a visual signal, not a regional CRAP score. Measured glow can obscure grey nodes; inspect nodes for provenance.

The target project's installed TypeScript resolves calls, constructors, JSX and function references through its type checker; Graphify contributes separately labeled inferred calls. Findings are matched by source location. Passed and configured functions are references, not proof of invocation. If TypeScript is unavailable the report explicitly says so and falls back to Graphify. Dynamic calls, framework relationships, exports and unresolved or ambiguous matches may be missing, and inferred edges may be wrong. A missing relationship is not proof of dead code. Source-backed package entry exports and module initialization are represented by unscored boundaries, not calls. The tool does not analyze external consumers. Spring links and an invisible file-tree attraction organize the graph; the latter is proportional to `2 / d`, where `d` is the total number of levels from both functions to their nearest common ancestor. Nodes in the same file have weight 1. The layout runs once and settles continuously; it does not search for a global optimum. The File location and Call connections sliders scale the file-tree attraction (including directory anchors) and inferred-call springs independently from 0% to 200%. Both default to 100%; 0% disables that force. Adjusting a slider reheats the current layout without resetting positions. Repulsion scales the node-repelling force from 0% to 300% (default 100%). Spring length sets the target call-edge length in simulation units (10–120; default 38). The Simulation heat indicator shows the current simulation alpha, from 1 down to the settling threshold of 0.003. When nodes are still, alpha decays by 1% per tick; changes to controls or dragging can reheat the graph. The decay is scaled by `max(0, 1 - movement / threshold)²`, where movement is the greatest per-tick displacement of any unpinned node and threshold is `max(0.01, sqrt(alpha))` simulation units. Cooling slows with movement and pauses at the threshold, which tightens as the graph cools. One persistent moving node can keep the simulation active. Inspired by ForceAtlas2, the worker estimates changes in each node’s applied force (swinging) versus consistent force (traction), smoothly adapts D3 velocity damping, and reduces the next-step velocity of oscillating nodes. When movement approaches the pause threshold, damping can increase up to 0.99 and then eases back. This is a D3 heuristic, not the ForceAtlas2 algorithm. It uses one continuous simulation and does not guarantee an optimum. Strong forces can sustain motion and delay settling. The initial positions still reflect directory grouping, even when file forces are set to zero.

The D3 force bundle uses d3-force 3.0.0; see [D3-LICENSE.txt](D3-LICENSE.txt). To rebuild after changes:

```sh
npm install --prefix /tmp/visual-crap-build d3-force@3.0.0 esbuild@0.28.1 --no-save --no-package-lock
NODE_PATH=/tmp/visual-crap-build/node_modules /tmp/visual-crap-build/node_modules/.bin/esbuild force-worker.js --bundle --minify --format=iife --outfile=force-worker.bundle.js --legal-comments=inline
```

## Binary releases

Every push to `main` builds and smoke-tests single-file macOS executables for Apple Silicon and Intel and a Linux x86-64 executable built on Ubuntu 22.04, then publishes a GitHub release with SHA-256 checksums. Releases start at `v0.1.0` and increment the patch version; include `#minor` or `#major` in a commit message to bump that component. Linux builds require glibc 2.35 or newer and are not built for musl-based distributions. Node.js and npm are still required to run Fallow. Download the matching archive from the repository's Releases page and run `visual-crap --help`. To build locally, run `./build.sh`; `VERSION=v1.2.3 ./build.sh` stamps a version.
